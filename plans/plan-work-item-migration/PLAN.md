## Outcome

Every in-scope outstanding plan has a verified canonical tracker identity or a precise unresolved
disposition. Personal work uses its explicitly selected GitHub provider; Infonetica work uses its
explicitly selected Azure provider. Design/recovery documents remain with their source owners and link
the tracker; status is maintained in the tracker. Recording does not start implementation or transfer
another live executor's ownership. Do not migrate completed work into a new open backlog.

## Scope and authority

The user approved the preceding proposal to inventory unfinished plans, reconcile duplicates and
existing tracker records, group features and their concrete work, and retain useful linked design docs.
This authorizes tracker creation/reconciliation and necessary scoped provider configuration. It does
not approve feature implementation, deletion of historical evidence, broad Git resets, policy-check
removal, credential widening, automatic assignment, new branches in employer repositories or adoption
inferred from an owner or directory. Agent Workboard retains its existing explicit exclusion.

## Mechanism decision

Assessment complete: use shipped Personal/Infonetica deterministic readers/creators, existing durable
request receipts and the native tracker hierarchy where supported. Do not add a migration service,
shared package or new backlog. Small disposable scripts may inventory and reconcile known sources.
Repository metadata and recorded explicit adoption establish scope. No alternate tracker is substituted.

## Execution and acceptance

1. Inventory actual primaries, worktree/global copies and selected providers; classify canonical plan
   families using the latest factual checkpoint, current tracker state and source ownership.
2. Reconcile all existing remote identities before creating missing records. Reuse known request IDs.
   Completed/superseded/recovery-only/ambiguous documents receive an evidenced disposition.
3. Configure only explicitly authorized missing provider bindings through supported setup, preserving
   unrelated dirty files, local permissions, existing selections and live owners.
4. Record repository-owned features and concrete children from the plans' actual remaining outcomes
   and acceptance conditions. Preserve dependencies, source links, legacy identities and uncertainty.
   Employer assignment/parent decisions remain explicit and employer evidence stays in Azure.
5. Read back every created/reused identity, verify grouping and backlinks, and publish appropriate
   personal source-plan/config changes through the normal review and delivery lifecycle.
6. Complete only when every inventoried canonical family is accounted for and all authorized work is
   delivered, or record exact genuine gates with their owner and observable resume condition.
